## Round 1 — loop-security (code-phase)

Reviewed: `mcp_honeypot.py` (new file, full contents) and the `.gitignore` one-line addition, against `plan.md` and the non-negotiable safety rules for Task 1 (HTTP transport, universal request-lifecycle logging including `log_error`/`handle_one_request` overrides, JSONL logging core).

**Forbidden-identifier sweep (verified against actual code, not comments):** `grep -n -E 'eval\(|exec\(|subprocess|socket\.socket|urllib|importlib'` matches only the safety-rule text inside the module docstring — zero occurrences in executable code. `open(` appears exactly once, at `main()` line 555, opening only `args.log_file` in append mode (`"a"`), matching "log file is append-only" and "never read/write files outside the log path." No `os.system`, `pickle`, `marshal`, `shutil`, `__import__`, `compile(`, `globals(`/`locals(` usage anywhere.

**Resource-exhaustion guardrails verified wired, not just documented:**
- `SOCKET_TIMEOUT_SECONDS = 10` is set as `HoneypotRequestHandler.timeout`, which `socketserver.StreamRequestHandler.setup()` applies as a real socket-level timeout — confirmed via class attribute, not just a comment.
- `MAX_CONCURRENT_CONNECTIONS` is enforced by a real `threading.BoundedSemaphore` in `HoneypotHTTPServer`: `process_request()` does a non-blocking `acquire()` in the single accept-loop thread and closes+drops the connection on failure; `process_request_thread()` releases in a `finally` in the worker thread. Semaphore acquire/release across threads is valid (semaphores aren't required to be released by the acquiring thread), so this pairing is correct with no leak path — every code path through `process_request_thread` (including exceptions inside `handle()`) still hits the `finally`.
- `MAX_BODY_BYTES` is enforced in `_classify_content_length`: `self.rfile.read(length)` is only ever called after `length` has been validated `<= MAX_BODY_BYTES`, so there's no path to an unbounded body read into memory. Oversized/invalid/duplicate/chunked framing is rejected (413/400/411) *before* any body bytes are read.
- `MAX_LEADING_BLANK_REQUEST_LINES` genuinely bounds the loop in the `handle_one_request()` override: each iteration reads at most 65537 bytes via `readline(65537)`, and the loop provably terminates after at most `MAX_LEADING_BLANK_REQUEST_LINES + 1` iterations (traced the loop condition manually) — it cannot spin indefinitely on an attacker sending an unbounded stream of blank lines.

**Thread safety of the log writer verified:** `JSONLogWriter` is instantiated exactly once in `main()` (global `log_writer`), wraps a single file handle, and every write path (`_handle_request`, `log_error`, `_log_blank_request_line`, `_emergency_fallback`) calls the same `log_writer.write()`, which lock-guards `write()+flush()` as one critical section. No second `open()`/file handle is created anywhere, including in the `log_error` and `_emergency_fallback` fallback paths — confirmed via the single-`open()` grep above. No race window found.

**Log-injection defenses verified:** `sanitize_for_stderr` strips all bytes `<= 0x1f` and `0x7f` (covering `\n`, `\r`, ESC/ANSI sequences) before anything reaches stderr, and truncates to 300 chars — confirmed this is applied on every `emit_stderr_summary` call site. The JSONL path relies on `json.dumps`, which per RFC 8259 always escapes control characters (including newlines) inside string values, so a hostile header/body/tool-argument value cannot break JSONL line structure or forge a second fake record. No manual string concatenation of untrusted values into either the JSONL line or a shell/SQL/template context anywhere in the file.

| Severity | Finding | Location |
|---|---|---|
| minor | `_classify_content_length`'s validity check uses `raw.isdigit()`, which returns `True` for non-ASCII Unicode digit characters (e.g. U+00B2 `²`) that `int()` cannot parse in base 10, causing an uncaught `ValueError` inside the helper for a crafted `Content-Length` value. This is fully caught by the outer `try/except Exception` in `_handle_request` (degrades to a logged 500 `internal_fault` instead of a clean 413) — not a crash, not a bypass of the body-size cap, not exploitable for resource exhaustion — but it's a correctness gap in input validation at a trust boundary. Recommend `raw.isascii() and raw.isdigit()`, `raw.isdecimal()`, or wrapping `int(raw)` in its own try/except. | `mcp_honeypot.py:94-97` (`_classify_content_length`) |
| minor | The four body-framing-rejection outcomes (`chunked` -> 411, `duplicate_content_length`/`duplicate_transfer_encoding` -> 400, `missing_or_invalid` -> 413) never read/drain the client's pending body bytes and never set `self.close_connection = True`. On a keep-alive connection this can cause the next `parse_request()` call to misinterpret leftover body bytes as the next request line. This is self-contained to the offending client's own connection (this is an origin server, not a proxy, so it is not a request-smuggling vector against other clients), and is naturally bounded by the existing per-line read cap and socket timeout, so it is not a DoS vector — but it undermines clean per-connection logging fidelity, which matters for a honeypot. Recommend explicitly setting `self.close_connection = True` on all four outcomes. | `mcp_honeypot.py:411-423` (`_handle_request`) |
| minor | `json.dumps` (used unmodified, `allow_nan=True` default) will happily serialize Python `float('nan')`/`inf` values into bare `NaN`/`Infinity`/`-Infinity` tokens, which are not valid per RFC 8259. Since `json.loads` (also used with defaults) accepts these same non-standard tokens on the way in, a client can send a JSON-RPC body containing `NaN`/`Infinity` (e.g. inside `tool_arguments`) and have it round-trip into the JSONL log as syntactically-non-standard JSON, mildly contradicting the module docstring's claim that "the JSONL write is structurally safe via json.dumps." Not a control-character/newline log-injection issue (line structure/boundaries are unaffected) and not exploitable beyond a downstream strict-JSON-parser compatibility wart. Consider `json.dumps(record, allow_nan=False)` with a substitution/sanitization fallback if strict RFC 8259 output is desired. | `mcp_honeypot.py:226` (`JSONLogWriter.write`) |

No blocking or major findings. All four stated resource-exhaustion mitigations (`SOCKET_TIMEOUT_SECONDS`, `MAX_CONCURRENT_CONNECTIONS` via `BoundedSemaphore`, `MAX_BODY_BYTES`, `MAX_LEADING_BLANK_REQUEST_LINES`) are correctly wired in the actual code, not just described in comments. No forbidden identifiers (`eval`, `exec`, `subprocess`, `socket.socket`, `urllib`, `importlib`, extra `open(`) appear anywhere in executable code. `JSONLogWriter` is a single lock-guarded instance with no duplicate/second file handle on any path, including `log_error` and `_emergency_fallback`. Log-injection defenses (stderr control-character stripping, JSONL structural safety via `json.dumps`) are correctly applied on every code path that writes to either sink.

**Verdict:** APPROVED
