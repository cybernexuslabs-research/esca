# Security Plan Review: Build a minimal MCP (Model Context Protocol) honeypot in Python.

Purpose: A decoy MCP server that appears to expose useful tools, logs everything a client does, and never performs any real action. Intended for observing how LLM agents and automated scanners interact with untrusted MCP servers.

Scope for v1: Single file, stdlib plus at most one small dependency. No database, no web UI, no alerting. Getting complete, well-structured logs is the only goal.

Protocol surface: Serve MCP over streamable HTTP on a configurable host/port (default 127.0.0.1:8000). Handle enough JSON-RPC 2.0 to keep a real client talking: initialize (return protocolVersion, serverInfo, capabilities [tools only]), notifications/initialized, tools/list (return the fake tool catalog), tools/call (return canned fake results), ping. Any unknown method returns a well-formed JSON-RPC error rather than crashing or closing the connection. Malformed JSON gets a -32700 parse error and is still logged.

Fake tool catalog: Four tools with realistic names, descriptions, and JSON Schemas -- plausible enough that an agent would try them, e.g. a file reader, a database query runner, a credential/secret lookup, and an outbound email sender. Each returns static or templated fake data. Nothing touches the filesystem, network, shell, or any real service.

Logging: Append one JSON object per line to a JSONL file (default ./honeypot.jsonl): ISO 8601 UTC timestamp; source IP and port; request HTTP headers (at minimum User-Agent); session identifier, if the client provides one; the raw request body as received; the parsed method name, and for tools/call the tool name and full arguments; the response the honeypot returned. Log before responding so nothing is lost if a handler raises. Also mirror a one-line human-readable summary to stderr.

Safety rules (non-negotiable): Never eval, exec, subprocess, or import anything derived from client input. Never make outbound network requests. Never read or write files outside the log path. Log file is append-only; treat every logged value as untrusted text.

Deliverables: The honeypot source file. A one-paragraph README: how to run it, where logs go, how to point an MCP client at it for testing.

Findings from `loop-security` (plan-phase), appended one `## Round N` section per round. See `review-notes.md` for the parallel plan-quality findings on the same rounds.

## Round 1 — loop-security (plan-phase)

Reviewed `plan.md` and `design.md` on branch `goal/mcp-honeypot` against the stated non-negotiable containment constraints (no eval/exec/subprocess/dynamic-import of client input, no outbound network calls, no file access outside the log path, append-only/injection-safe logging, and DoS resistance for a server explicitly meant to sit exposed to hostile clients).

**Constraints that are well-covered by the design:**
- No `eval`/`exec`/`subprocess`/dynamic `import` of client input: tool handlers are specified as pure functions over parsed arguments only; Tasks 3 and 4 both mandate an explicit `grep` gate (`eval(`, `exec(`, `subprocess`, `socket.socket`, `urllib`, `importlib`, stray `open(`) as an acceptance criterion, and code-phase review can re-verify this mechanically.
- No outbound network requests / no SSRF: no network-related stdlib modules appear anywhere in the module list; the design correctly avoids validating/resolving anything client-supplied. (Verified separately: modern `http.server.BaseHTTPRequestHandler.address_string()` no longer performs reverse-DNS on the client IP in Python 3, so there's no implicit DNS side channel from the transport layer either.)
- No file access outside the log path: the `read_file` fake tool is explicitly specified to echo the requested path into templated fake content *without ever calling `open()` on it* — the design correctly identifies and forecloses the obvious path-traversal trap here, and the log file itself is opened exactly once, in `main()`, from an operator-supplied (not client-supplied) `--log-file` argument.
- Log injection / structure corruption: the JSONL record is built as a Python dict and serialized with `json.dumps`, so embedded newlines/control characters in any client-controlled field (headers, body, tool arguments) are string-escaped by construction and cannot break line framing or forge adjacent log lines. The separate stderr mirror has its own `sanitize_for_stderr` step (strip `[\x00-\x1f\x7f]`, bounded length) specifically because that channel isn't JSON-encoded — this is the correct place to worry about it and the design calls it out explicitly in Risks.

**Gaps relative to the DoS-resistance / containment bar the review brief calls for:**

| Severity | Finding | Location |
|---|---|---|
| major | Design specifies a request-body size cap but no read/idle timeout on the HTTP connection and no cap on concurrent connections/threads. `ThreadingHTTPServer` + `BaseHTTPRequestHandler` block forever by default (`timeout = None`) on a slow/silent client, and there's no `request_queue_size`/connection-count guard anywhere in the design. For a server the plan itself frames as eventually being rebound to `0.0.0.0` to act as a real decoy, this is a trivial slowloris-style thread-exhaustion vector (one thread per stalled connection, unboundedly). The plan's Risks section acknowledges the underlying gap but resolves it with only a README warning ("rebinding to 0.0.0.0 ... removes the only implicit protection") rather than a cheap code-level guardrail (e.g., `HoneypotRequestHandler.timeout` + `handle_timeout`, `ThreadingHTTPServer.daemon_threads = True`, or a bounded semaphore on concurrent handler threads) that costs essentially nothing in "catch rate" but meaningfully raises the resource-exhaustion bar. | design.md § Architecture Overview / Risks (plan.md § Risks, "ThreadingHTTPServer has no built-in connection/thread limits") |
| major | The in-memory `SESSIONS` dict has no size cap, eviction, or per-client rate limit. Every `initialize` call (unauthenticated, no cost to the caller, arbitrarily repeatable) adds one more entry via `uuid.uuid4().hex` with no expiry. Combined with the missing connection-count guard above, a hostile client can sustain many connections each issuing repeated `initialize` calls to grow this structure without bound — a second, independent memory-exhaustion vector beyond the body-size cap that the design doesn't address. | design.md § Data Flow / Interfaces, "Session-id issuance"; § Components / Modules, "Session store" |
| major | The catch-all exception handling described in plan.md ("a catch-all exception handler around each request so any internal error becomes a logged -32603 ... instead of a crash or a hung/dropped connection") is implemented in the design only as a `try/except Exception` *inside* `dispatch()`, wrapping handler-function calls. It does not visibly wrap the earlier transport-layer steps in `do_POST` — bounded body read, UTF-8 decode, and `json.loads`. A crafted body that raises something other than `json.JSONDecodeError` during parsing (e.g. deeply nested JSON pushing `json.loads` past Python's recursion limit and raising `RecursionError`, which is a `RuntimeError`/`Exception` subclass but is *not* caught if only `JSONDecodeError` is caught at that call site) would propagate out of `do_POST` before `build_log_record`/`log_writer.write` ever runs. Net effect: a request that crashes the handler thread produces **no log line at all**, which is both a robustness gap and a logging-evasion technique available to a hostile client against the honeypot's core purpose (complete logs). Design should specify one top-level `try/except Exception` wrapping the entire per-request sequence in `do_POST` (read → decode → parse → dispatch → log → respond), not just the dispatch-internal one. | design.md § Data Flow / Interfaces (request lifecycle diagram); Task Breakdown Task 1/2 |
| minor | Unbounded JSONL log growth on disk has no design-level mitigation (log rotation/size cap is explicitly out of scope per plan.md, and design doesn't add an alternative such as a max-file-size guard or per-source rate limit). Since every request that parses as JSON — including a rapid stream of minimal, well-formed `ping` calls — gets one flushed, disk-durable log line, a hostile client can drive unbounded disk consumption at essentially the price of raw request throughput. This is a known, documented tradeoff (plan.md explicitly frames log management as an operator concern), but given the review brief's instruction to flag disk exhaustion even though out of the explicit non-negotiable list, it's worth at minimum an explicit README caveat alongside the connection-limit warning, or a minimal safeguard (e.g., stop-writing-and-signal-full-disk behavior rather than an unbounded `write+flush` loop). | plan.md § Out of Scope ("Log rotation, retention limits..."); design.md § Concurrency and durability |
| minor | No explicit design-level cap on HTTP header count/size — the design relies implicitly on stdlib `http.client` internal limits (header count/line-length ceilings) without calling this out as an intentional reliance. Low risk in practice since the stdlib limits exist, but worth stating explicitly as a documented assumption rather than leaving it implicit, so a future maintainer doesn't inadvertently swap in a handler base class without those limits. | design.md § Architecture Overview, HTTP handler component |

**Verdict:** CHANGES REQUESTED

Rationale: the hard, non-negotiable constraints around code/command injection, SSRF, and path traversal are well-designed and backed by concrete static-verification gates (Tasks 3/4's grep checks) — no blocking findings there. However, given this server's explicit purpose is direct exposure to hostile/automated clients, the design currently has three independent, easily-triggerable resource-exhaustion vectors (unbounded thread/connection lifetime, unbounded session-store growth, and a logging code path that can be bypassed by an uncaught exception before the log write happens) that aren't adequately addressed by "cap the body size" plus a README warning alone. These are cheap to close at design time (timeouts, a session cap/expiry, and widening the catch-all to the whole request path) and should be folded into `design.md` before implementation rather than left for code-phase review to catch after the fact.

**Specific check requested: does `log_error()` introduce a new log-flooding / disk-exhaustion DoS worse than before?**

Traced the achievable trigger rate for the new `log_error`-sourced records against the already-accepted (Round 1, minor, resolved-via-README-caveat) risk that *any* logged traffic — including a trivial `ping` flood — drives unbounded, un-rate-limited, flush-per-write JSONL growth:

- Every `log_error`-sourced record goes through the exact same `log_writer.write()` (lock-guarded, `flush()`-per-record per design.md:43/392) as every normal request record, so it doesn't bypass or amplify past the existing write path.
- The stdlib-rejection cases this override newly logs (malformed/oversized request line, unsupported HTTP version, oversized headers, unimplemented verb, pre-request-line stall) each still cost the attacker one TCP connection (protocol default is `HTTP/1.0`, no keep-alive, per design.md:158, so this holds for both normal and rejected traffic) and are still gated by the same `MAX_CONCURRENT_CONNECTIONS` semaphore as ordinary requests. Constructing a garbage request line is marginally cheaper than constructing a valid minimal `ping` POST, but the dominant cost in both cases is TCP connect/accept/teardown, not the few extra bytes of a well-formed body — so the achievable disk-write rate via this new path is not meaningfully higher than the already-accepted `ping`-flood case.
- Conclusion: this is **not a new order-of-magnitude DoS vector** beyond what Round 1 already accepted and documented as an operator responsibility. It does, however, widen the *set of traffic* that now contributes to that already-accepted risk (previously-silent malformed/garbage requests now also write+flush a JSONL line), and the Round 2 disposition table's framing of this fix as pure completeness gain doesn't mention that tradeoff anywhere, nor does Task 4's README caveat (design.md:536, "unbounded disk growth under sustained traffic") make clear that rejected/malformed traffic is now included in "traffic" for this purpose. Worth a documentation update, not a design fix.

**New findings from this round (all minor):**

| Severity | Finding | Location |
|---|---|---|
| minor | The `log_error()` override (design.md:210-238) is written less defensively than `_handle_request`. `_handle_request`'s entire body is wrapped in one outer `try/except Exception` feeding `_emergency_fallback`, and each of `_emergency_fallback`'s three actions is individually wrapped in its own `try/except Exception: pass`. `log_error()` only wraps the `log_writer.write(record)` call; `build_stdlib_rejection_record(...)` (including its `headers_to_dict(self.headers)` call) and `format % args` are unwrapped. If either ever raised on some edge-case partial-parse state (e.g. `self.headers` present-but-malformed at the exact point a header-parsing exception fired), the exception would propagate out of `log_error()` into the stdlib's own `send_error()`/`handle_one_request()`, meaning (a) `super().log_error(...)` is never reached, so the stdlib's own operator-facing diagnostic line is lost, and (b) the exception is caught only by `socketserver`'s generic `handle_error()`, which prints an **unsanitized** traceback straight to stderr — bypassing `sanitize_for_stderr` entirely, inconsistent with this design's otherwise-consistent care about not letting attacker-influenced text hit stderr unescaped (the `detail` string can contain up to ~64KB of attacker-controlled request-line bytes via `%r` formatting of stdlib exceptions). Recommend wrapping the record-build-and-log portion of `log_error()` in the same `try/except Exception: pass` pattern used everywhere else in the file, so `super().log_error(...)` is unconditionally reached regardless of what happens above it. | design.md:210-238, "Universal logging via a `log_error` override" |

**Specific check requested: does `handle_one_request()` — a near-verbatim reproduction of stdlib internals — introduce request smuggling, a bound-bypass, or a socket-timeout/semaphore bypass?**

Traced the override (design.md:280-357) line-by-line against actual CPython `BaseHTTPRequestHandler.handle_one_request()` source (the design's own transcription is accurate to the version reviewed in Round 3):

- **No misparse/smuggling introduced.** The override only changes *what happens before* the first non-blank line is treated as the candidate request line; once a candidate line is selected (either non-blank, or blank-but-bound-exhausted), it is handed to the *unmodified* `self.parse_request()` exactly as in stock CPython. Each loop iteration consumes exactly one complete line via `self.rfile.readline(65537)` before deciding whether to skip or break — no partial-line buffering or byte-level realignment occurs, so body bytes can never be misinterpreted as header/request-line bytes or vice versa. The `>65536`-byte-line and zero-byte-EOF branches are reproduced verbatim inside the loop and behave identically to stock behavior on every iteration, not just the first.
- **No bypass of `MAX_LEADING_BLANK_REQUEST_LINES`.** Traced the exact counter arithmetic: the loop logs and increments `blank_lines_skipped` on iterations 1 through `MAX_LEADING_BLANK_REQUEST_LINES` (5 by default), and the 6th line read (blank or not) always breaks out of the loop via the `blank_lines_skipped >= MAX_LEADING_BLANK_REQUEST_LINES` disjunct, regardless of its content. This matches the design's own stated acceptance criterion (design.md:603, 643) precisely — exactly 5 logged records, then termination or fallthrough on the 6th line, in every case. No client-controlled input (line length, content, timing) can make the loop iterate a 7th time.
- **No bypass of the socket timeout or connection-cap semaphore.** `HoneypotRequestHandler.timeout` is a class attribute applied once by `socketserver.StreamRequestHandler.setup()` at the socket level (`settimeout()`), so it governs *every* `self.rfile.readline()` call transparently, including each iteration of the new loop — a client stalling between blank lines still trips `TimeoutError`, caught by the same unmodified `except TimeoutError` clause the override preserves verbatim (design.md:328-332), which sets `close_connection = True` and returns, allowing `process_request_thread`'s `finally: self._conn_semaphore.release()` (design.md:576-580) to run normally. Nothing in the new loop acquires the semaphore, spawns a thread, or defers the `finally` release; the override runs entirely within the single handler thread the semaphore already accounts for.

No blocking or major findings from this check — the override is a faithful, correctly-bounded reproduction of stdlib behavior with one properly-guarded insertion, not a new vulnerability class.

**Specific check requested: can the blank-line skip-and-log loop itself be abused as an alternate resource-exhaustion vector?**

- **Per-connection hold time is bounded but not previously quantified.** Because `SOCKET_TIMEOUT_SECONDS` is a per-read idle timeout that resets on every call (the same property already named and accepted for body reads under `[SEC2-a]`, design.md:35), a client can trickle up to `MAX_LEADING_BLANK_REQUEST_LINES` blank lines, each withheld until just under the timeout, extending one connection's worst-case hold time from roughly 1×`SOCKET_TIMEOUT_SECONDS` (stock behavior, pre-fix) to roughly (`MAX_LEADING_BLANK_REQUEST_LINES` + 1)×`SOCKET_TIMEOUT_SECONDS` — about 60s at current defaults — before the bound forces termination. This is strictly smaller than the already-accepted, effectively-unbounded-in-practice body-trickle residual under `[SEC2-a]` (bounded only by `MAX_BODY_BYTES` × `SOCKET_TIMEOUT_SECONDS`, i.e. a much larger ceiling), so it is not a new order of magnitude of risk and the `MAX_CONCURRENT_CONNECTIONS` semaphore still caps the blast radius exactly as it does for every other slow-connection variant. However, this specific multiplier is not stated anywhere in the design (§ Architecture Overview's `[SEC2-a]` subsection, § Data Flow, or the README caveat all describe the *general* per-read-not-total-duration tradeoff but don't note that this particular code path multiplies the worst case by up to `MAX_LEADING_BLANK_REQUEST_LINES + 1`), which is a minor gap in the design's otherwise-precise practice of quantifying every bound it introduces.
- **Distinct from the timing question, `_log_blank_request_line()` produces disk-write amplification per accepted connection that the design's own Round 3 flooding analysis doesn't account for.** Round 3's security review (this file, lines 83-89 above) concluded the `log_error()` override doesn't materially lower attacker cost-per-log-line versus an ordinary `ping` flood, reasoning that "the dominant cost in both cases is TCP connect/accept/teardown" and each rejected connection produces exactly one flushed JSONL write. The new `handle_one_request()` override changes that accounting for this specific path: a single accepted TCP connection (consuming one of only `MAX_CONCURRENT_CONNECTIONS` = 200 slots) that sends `MAX_LEADING_BLANK_REQUEST_LINES` blank lines in quick succession (no need to trickle slowly — sending them back-to-back is *cheaper* for the attacker and still produces 5 separate lock-guarded `write()+flush()` calls, design.md:334-356) yields up to 5 flushed disk writes per one connect()/accept() cycle, versus 1 write for an ordinary request or an ordinary stdlib-rejected request. That is a real, roughly 5x reduction in attacker cost-per-log-line specifically via this new code path, achievable by any client regardless of whether it also tries to hold the connection open — it doesn't require slow-trickling at all, just sending 5 back-to-back blank lines before a real (or absent) request line, so connections can be cycled through quickly to sustain a higher aggregate write rate than the `[SEC1-Round3]` analysis assumed. This doesn't defeat containment (writes remain lock-serialized, and the underlying "unbounded JSONL growth under sustained traffic" risk was already accepted wholesale as an operator responsibility with no rotation in v1 — a constant multiplier on an already-accepted, already-unbounded-by-design risk doesn't change its category), but it does mean the specific "not meaningfully higher than the ping-flood baseline" rationale from Round 3 no longer fully holds for this path, and is worth either a one-line acknowledgment in the design/README or a note that `MAX_LEADING_BLANK_REQUEST_LINES` was chosen for logging-fidelity reasons (bounding the "unbounded skip loop" concern it was originally introduced to fix) rather than for disk-exhaustion-rate reasons, so a future reader doesn't conflate the two.

**Verdict:** APPROVED

Rationale: both Round 3 minor notes this round was asked to verify are genuinely and precisely resolved — `log_error()`'s full-body defensive wrap (and the identical pattern applied to the new `_log_blank_request_line()` helper) means a bug in the new logic can never suppress the stdlib's own error response or leak an unsanitized traceback, and the README's disk-growth caveat now explicitly names rejected/malformed traffic as a contributing source. The new `handle_one_request()` override, despite being a near-verbatim reproduction of stdlib internals as the architect describes it, does not introduce request smuggling, a way to misparse subsequent bytes, a way to exceed `MAX_LEADING_BLANK_REQUEST_LINES`, or a way to bypass the socket timeout or the `MAX_CONCURRENT_CONNECTIONS` semaphore — traced line-by-line, the loop consumes exactly one complete line per iteration, the counter arithmetic is exact and unbypassable, and the pre-existing `TimeoutError` handling (and therefore the semaphore's `finally`-guarded release) is preserved verbatim and fires on every iteration, not just the first. This round's three new findings are all minor and narrow: a previously-unstated (but bounded and smaller-than-already-accepted) connection-hold-time multiplier, a real but non-containment-breaking ~5x disk-write-amplification-per-connection specific to the blank-line path that slightly undercuts Round 3's own flooding-cost reasoning, and a forward-compatibility note that the bound's "per connection" framing silently depends on `protocol_version` never being changed to enable keep-alive. None are blocking or major; implementation can proceed, and these are worth folding into a design touch-up or flagging for code-phase review to verify the constants/comments land as described.
