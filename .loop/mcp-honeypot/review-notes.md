# Plan Review Notes: Build a minimal MCP (Model Context Protocol) honeypot in Python.

Purpose: A decoy MCP server that appears to expose useful tools, logs everything a client does, and never performs any real action. Intended for observing how LLM agents and automated scanners interact with untrusted MCP servers.

Scope for v1: Single file, stdlib plus at most one small dependency. No database, no web UI, no alerting. Getting complete, well-structured logs is the only goal.

Protocol surface: Serve MCP over streamable HTTP on a configurable host/port (default 127.0.0.1:8000). Handle enough JSON-RPC 2.0 to keep a real client talking: initialize (return protocolVersion, serverInfo, capabilities [tools only]), notifications/initialized, tools/list (return the fake tool catalog), tools/call (return canned fake results), ping. Any unknown method returns a well-formed JSON-RPC error rather than crashing or closing the connection. Malformed JSON gets a -32700 parse error and is still logged.

Fake tool catalog: Four tools with realistic names, descriptions, and JSON Schemas -- plausible enough that an agent would try them, e.g. a file reader, a database query runner, a credential/secret lookup, and an outbound email sender. Each returns static or templated fake data. Nothing touches the filesystem, network, shell, or any real service.

Logging: Append one JSON object per line to a JSONL file (default ./honeypot.jsonl): ISO 8601 UTC timestamp; source IP and port; request HTTP headers (at minimum User-Agent); session identifier, if the client provides one; the raw request body as received; the parsed method name, and for tools/call the tool name and full arguments; the response the honeypot returned. Log before responding so nothing is lost if a handler raises. Also mirror a one-line human-readable summary to stderr.

Safety rules (non-negotiable): Never eval, exec, subprocess, or import anything derived from client input. Never make outbound network requests. Never read or write files outside the log path. Log file is append-only; treat every logged value as untrusted text.

Deliverables: The honeypot source file. A one-paragraph README: how to run it, where logs go, how to point an MCP client at it for testing.

Findings from `loop-plan-reviewer`, appended one `## Round N` section per round. See `security-plan-review.md` for the parallel security findings on the same rounds.

**New finding this round**, found by reading the actual CPython 3.10+ `http.server` source (`BaseHTTPRequestHandler.handle_one_request`/`parse_request`) rather than taking the design's stdlib claims on faith:

| Severity | Finding | Location |
|---|---|---|
| major | § Architecture Overview and § Data Flow both assert there are exactly **two** named exceptions to "every request is logged": (1) HTTP verbs outside the seven implemented `do_*` methods, and (2) requests that trip the stdlib header-count/line-length limits. Verified against the actual stdlib source that this enumeration is incomplete — several other realistic scenarios also never reach `_handle_request` and therefore never produce a JSONL record: (a) a request line that doesn't parse as `METHOD SP PATH SP HTTP/x.y` (e.g. garbage/non-HTTP bytes, a bare port-scanner banner probe, an HTTP/0.9-style non-GET request, an unsupported HTTP major version) is rejected inside `parse_request()` via `send_error(400)`/`send_error(505)` before `do_*` is ever invoked; (b) a request line longer than 65536 bytes gets `send_error(414)` from `handle_one_request()` itself, before `parse_request()` even runs; (c) a client that connects but sends nothing before the request line arrives (i.e., stalls *before* any HTTP verb/path is known, not mid-body) hits `TimeoutError` inside `handle_one_request`'s own try/except and the connection is silently discarded — this is a distinct case from the "slow body" scenario Task 1's acceptance criteria test, and it also produces zero honeypot.jsonl record. For a tool whose stated purpose is complete logs of "every request/response" from exactly the kind of raw scanner/protocol-probing traffic that would trigger these paths, understating the true scope of the gap (as "two named exceptions") risks the architect/builder treating the logging-completeness question as fully closed when it isn't. | minor | `_emergency_fallback`'s spec says it "attempts, only if no response bytes have been sent yet, to send a generic HTTP 500" but no mechanism for tracking "has a response already been sent" is named anywhere in § Components/Modules or § Data Flow's function signatures (no `self._response_sent`-style flag or equivalent is declared). This is a small, easily-inferable detail (set a flag right before/after the real `wfile` write completes in `_send_response`), but it's exactly the kind of "builder has to invent it" gap the review brief asks to catch, especially since getting it wrong (e.g. attempting to send a second status line after headers were already flushed) could corrupt the HTTP response on the one code path meant to be the last line of defense against a broken connection. | design.md § Data Flow / Interfaces, `_emergency_fallback` description (line ~129) |
| minor | `validate_arguments`'s type-check spec maps JSON Schema `"integer"`/`"number"` to a Python `isinstance(value, int)` / `isinstance(value, (int, float))` check, but doesn't account for Python's `bool` being a subclass of `int` — so a `tools/call` argument value of `true`/`false` would incorrectly pass validation for a schema field declared `"type": "integer"` or `"type": "number"`, contrary to JSON Schema semantics (which treat booleans and numbers as distinct types). Low real-world impact for a honeypot's fake validation, but worth a one-line spec fix (`type(value) is int` or an explicit `isinstance(value, bool)` exclusion) so `validate_arguments`'s stated behavior actually matches JSON Schema. | design.md § Data Flow / Interfaces, `validate_arguments` signature/docstring (line ~195-201) |
| minor | `_validated_content_length()`'s behavior for a `Transfer-Encoding: chunked` request (no `Content-Length` header at all, which is legal HTTP/1.1) isn't distinguished from a genuinely missing/invalid `Content-Length`: both fall into the same 413 path with the log marker `"(oversized or invalid Content-Length)"`, which is a misleading record for what's actually an unsupported transfer encoding rather than an oversized body. Since the design elsewhere is careful to make every logged marker precisely describe what happened, this one conflates two different causes. Worth either a distinct marker/status for chunked requests or an explicit one-line note that v1 doesn't support chunked transfer encoding and treats it identically to a missing Content-Length by design. | design.md § Data Flow / Interfaces, request-lifecycle pseudocode, `_validated_content_length()` (line ~76-79) |

Since this server terminates the HTTP connection itself (no upstream proxy in front of it in the documented deployment model) the practical exposure is low, but it's security-adjacent enough to note explicitly rather than leave to the implicit behavior of the underlying header-parsing library. | design.md § Data Flow / Interfaces, `_validated_content_length()` (line ~76) |

Practically, this also means a client that (per RFC 7230's own leniency recommendation) sends one leading blank line before its actual request line loses the *entire* subsequent request with zero trace, not just the blank line itself, since `handle_one_request()` doesn't loop back to read a second line on this path. Given how much weight this design (and Task 4's README text, "Exactly two narrow, named exceptions remain...") puts on precisely enumerating the logging gap, and given this is the exact scenario the review brief asked to verify empirically, this should be fixed (e.g. an additional targeted check/override, or accepting and looping past a single leading blank line before parsing, mirroring RFC 7230's own recommendation) or the disposition table / § Data Flow / Task 4 README text should be updated to name a third genuinely-unlogged case rather than continue asserting "exactly two." | design.md § Data Flow / Interfaces, "Universal logging via a `log_error` override" and "Universal logging: what's covered and what genuinely isn't" (lines ~197-248); design.md Task 4 README caveat text ("Exactly two narrow, named exceptions remain...", line ~538) |

## Round 4 — loop-plan-reviewer

Scope for this round: verify the three specific claims in design.md's "Round 3 revision" text and "Round 3 finding disposition" table against the actual section content and code — the `handle_one_request()` override's blank-line-skip loop, the revised three-item "what's covered and what genuinely isn't" list, and Transfer-Encoding/Content-Length duplicate-detection consistency. Traced the `handle_one_request()` override line-by-line against the logic it's meant to replace (not just read the prose).

**1. `handle_one_request()` override correctness.** Traced the loop by hand for the relevant cases:
- **Normal (non-blank) first line:** `raw_requestline.strip()` is truthy on the first iteration → immediate `break` → falls straight into `parse_request()` exactly as the unmodified stdlib does. No behavior change on the common-case path.
- **Single leading blank line (`b"\r\n"`) followed by a real request:** iteration 1 reads the blank line, `strip()` is falsy and `blank_lines_skipped (0) < MAX_LEADING_BLANK_REQUEST_LINES (5)`, so it logs via `_log_blank_request_line()`, increments to 1, and loops; iteration 2 reads the real line, breaks, parses normally. Matches the claimed fix and its acceptance criterion exactly.
- **`MAX_LEADING_BLANK_REQUEST_LINES + 1` (6) consecutive blank lines:** lines 1–5 are each individually logged (skipped count goes 0→1→2→3→4→5, condition `skipped >= 5` false each time until after the 5th). On the 6th read, `strip()` is still falsy but `blank_lines_skipped (5) >= 5` is now true, so the loop breaks with a still-blank `raw_requestline`, and falls through to `parse_request()`, which (per the documented stdlib bug) returns `False` silently — no log call. Net result: exactly 5 logged, the 6th line silently dropped. This matches the design's own claim and Task 1's acceptance criterion for this case precisely.
- **Bounded/no-infinite-loop:** each `readline()` call inside the loop is still subject to the per-connection `SOCKET_TIMEOUT_SECONDS` socket timeout (reset per read), and a stall raises `TimeoutError`, caught by the *same* outer `except TimeoutError` block that wraps the whole method — unchanged from the stdlib original. Combined with the `MAX_LEADING_BLANK_REQUEST_LINES` cap, the loop cannot spin unboundedly under attacker control (bounded by min(5 iterations, timeout)).
- **Oversized-line and true-EOF checks** (`len(raw_requestline) > 65536` and `not raw_requestline`) are preserved inside the loop, in the same order as the stdlib original, and fire correctly on every iteration, not just the first — so a client that sends one blank line then an oversized line, or one blank line then closes the connection, is still handled correctly (414 / silent EOF-close respectively).

No infinite loop, no regression to the normal-line path, and the bounded-skip semantics match what design.md and Task 1's acceptance criteria claim. This holds up.

**2. Revised three-item "what's covered and what genuinely isn't" list.** Verified against the actual code:
- Item 1 (semaphore-cap drop) and item 3 (bounded blank-line residual) check out exactly as described (see above for item 3).
- Item 2 (zero-byte clean EOF) is implemented correctly — `if not self.raw_requestline: self.close_connection = True; return` fires with no log call — but the list's prose describes it narrowly as "a client that opens a TCP connection and sends **zero bytes** before an ordinary clean close." In the actual code, this same silent-EOF branch also fires on any loop iteration *after* one or more blank lines have already been read and individually logged (e.g., client sends one blank `\r\n` — logged via `_log_blank_request_line()` — then clean-closes without ever sending a real request line). That's a materially broader condition than "sends zero bytes": bytes *were* sent and *were* logged, only the final clean-close itself (correctly) produces no additional record. The underlying behavior is correct and not a bug — there's nothing new to log at the close-after-blank-lines point — but given how much weight this design and the README text place on the list being "the complete, current, and precisely-derived list," the item-2 description should be broadened to something like "a client that clean-closes the connection instead of ever completing a real request line (whether zero bytes were sent, or only whitespace/blank lines were sent first)" so it doesn't undersell/mis-scope the case it's naming. Low severity — this is a wording-precision gap in an already-correct mechanism, not a functional gap.

**3. Transfer-Encoding vs. Content-Length duplicate-detection consistency.** Verified the `_classify_content_length()` code directly: both headers are read via `headers.get_all(...)` (never `.get()`), both check `len(values) > 1` for the duplicate case *before* any single-value interpretation is attempted (Transfer-Encoding duplicates → Transfer-Encoding value → Content-Length duplicates → Content-Length value, matching the function's own docstring precisely), both duplicate outcomes map to HTTP 400 with the same `"(duplicate X headers)"` log-marker phrasing, and the response-shape section explicitly states this is "the same treatment for the same reason." This is now genuinely consistent, not just claimed to be — the Round 3 minor finding is resolved.

No blocking or major issues found this round. The one minor finding is a documentation-precision nitpick on an already-correct mechanism.

| Severity | Finding | Location |
