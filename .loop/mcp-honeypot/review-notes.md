# Plan Review Notes: Build a minimal MCP (Model Context Protocol) honeypot in Python.

Purpose: A decoy MCP server that appears to expose useful tools, logs everything a client does, and never performs any real action. Intended for observing how LLM agents and automated scanners interact with untrusted MCP servers.

Scope for v1: Single file, stdlib plus at most one small dependency. No database, no web UI, no alerting. Getting complete, well-structured logs is the only goal.

Protocol surface: Serve MCP over streamable HTTP on a configurable host/port (default 127.0.0.1:8000). Handle enough JSON-RPC 2.0 to keep a real client talking: initialize (return protocolVersion, serverInfo, capabilities [tools only]), notifications/initialized, tools/list (return the fake tool catalog), tools/call (return canned fake results), ping. Any unknown method returns a well-formed JSON-RPC error rather than crashing or closing the connection. Malformed JSON gets a -32700 parse error and is still logged.

Fake tool catalog: Four tools with realistic names, descriptions, and JSON Schemas -- plausible enough that an agent would try them, e.g. a file reader, a database query runner, a credential/secret lookup, and an outbound email sender. Each returns static or templated fake data. Nothing touches the filesystem, network, shell, or any real service.

Logging: Append one JSON object per line to a JSONL file (default ./honeypot.jsonl): ISO 8601 UTC timestamp; source IP and port; request HTTP headers (at minimum User-Agent); session identifier, if the client provides one; the raw request body as received; the parsed method name, and for tools/call the tool name and full arguments; the response the honeypot returned. Log before responding so nothing is lost if a handler raises. Also mirror a one-line human-readable summary to stderr.

Safety rules (non-negotiable): Never eval, exec, subprocess, or import anything derived from client input. Never make outbound network requests. Never read or write files outside the log path. Log file is append-only; treat every logged value as untrusted text.

Deliverables: The honeypot source file. A one-paragraph README: how to run it, where logs go, how to point an MCP client at it for testing.

Findings from `loop-plan-reviewer`, appended one `## Round N` section per round. See `security-plan-review.md` for the parallel security findings on the same rounds.

## Round 1 — loop-plan-reviewer

| Severity | Finding | Location |
|---|---|---|
| blocking | Design explicitly decides **not** to log HTTP-level rejections (404 for unknown paths, 405 for `GET`/`DELETE /mcp`) — only `POST /mcp` JSON-RPC exchange attempts (plus the one carved-out 413 case) ever produce a JSONL record or stderr line. This directly contradicts plan.md's own language: "JSONL logging: **one record per HTTP request**" (§ Approach) and the Goal's "produces complete, append-only JSONL logs of **every request/response**" — echoed verbatim atop design.md itself ("Getting complete, well-structured logs is the only goal"). A `GET /mcp` probe (which the MCP spec explicitly permits real clients to send, to check for SSE support, before falling back to plain POST) or any scanner enumerating paths would leave **zero trace** in the honeypot's output. For a tool whose entire purpose is observing what clients/scanners do, silently dropping reconnaissance traffic is a scope-defeating gap, not a minor omission. Resolve by either (a) logging every HTTP request including transport-level rejections (recommended — cheap, and matches the plan's stated language), or (b) explicitly walking back plan.md's "one record per HTTP request" / "every request/response" wording to "one record per JSON-RPC exchange attempt" so both documents agree and the trade-off is a deliberate, visible decision rather than something the builder discovers mid-implementation. | plan.md § Approach ("Logging record shape") and § Goal; design.md § Data Flow / Interfaces, lines ~71 |
| major | `Mcp-Session-Id` propagation is internally contradictory. "Core function signatures" declares `dispatch(msg, ctx) -> dict \| None`, but the "Session-id issuance" paragraph describes `handle_initialize` returning a tuple `(result_dict, new_session_id)` that "only `do_POST` unpacks," while separately claiming `dispatch()`'s contract "stays returns the response dict directly" for every method. It's never actually specified how the tuple gets from `handle_initialize` through `dispatch()` (whose declared signature has no room for a tuple) to `do_POST`. The design claims this asymmetry is "documented ... so the builder doesn't need to invent it ad hoc," but as written the builder still has to invent the actual plumbing. Needs one concrete, consistent contract (e.g. `dispatch()` always returns `(response_or_None, new_session_id_or_None)`, or a mutable out-parameter/module-level "pending session" slot) before Task 2 is buildable without guessing. | design.md § Data Flow / Interfaces, "Core function signatures" (dispatch signature) vs. "Session-id issuance" paragraph |
| major | plan.md commits to a `-32602 Invalid params` error path ("unparseable JSON, unknown method, bad params, internal handler error — gets HTTP 200 with a JSON-RPC error object (`-32700`, `-32601`, `-32602`, `-32603` respectively)"), but design.md never implements or tasks out `-32602` anywhere: it's absent from the `dispatch()`/handler contracts, from Task 2's method-handling breakdown, and from every task's acceptance criteria (only `-32700`, `-32601`, `-32603` appear). Either add a params-validation path that emits `-32602` (with an acceptance criterion to test it), or revise plan.md's promised error-code set down to what design.md actually delivers so the two documents agree. | plan.md § Approach ("HTTP status vs. JSON-RPC error split"), line 50; design.md § Task Breakdown, Task 2 |
| major | Request-lifecycle pseudocode branches on `"id" not in parsed` without first confirming `parsed` is a dict. If the POST body is syntactically valid JSON but not an object (e.g. `42`, `"hi"`, `[1,2,3]`, `true`) — very plausible input from a scanner fuzzing JSON-RPC endpoints — `json.loads` succeeds (`parsed is not None`), but `"id" not in parsed` raises `TypeError` on a non-container value. That exception fires in `do_POST` *before* `dispatch()` is ever called, i.e. **outside** the one try/except both documents call out as the non-negotiable safety net ("any internal error becomes a logged `-32603` ... instead of a crash or a hung/dropped connection"). Design should add an explicit `isinstance(parsed, dict)` (and ideally a `"jsonrpc"`/`"method"` shape check) before the `"id" not in parsed` branch, routing non-object JSON to a `-32600 Invalid Request`-style logged response instead of an unhandled exception. | design.md § Data Flow / Interfaces, request-lifecycle pseudocode, lines ~55-64 |
| major | § Components' "Session store" bullet claims the design will "attach a session_id if the client didn't send `Mcp-Session-Id` on a later call but did on `initialize`" — implying some correlation of later, header-less requests back to a previously-issued session. But § Data Flow's `RequestContext.session_id` is documented as coming strictly "from `Mcp-Session-Id` request header if present, else `None`" (no fallback lookup), and no correlation key for the fallback (client IP? something else?) is ever specified anywhere. Either drop the fallback-correlation claim from Components to match what Data Flow actually implements, or specify the correlation key and its known limitation (correlating by IP alone will misattribute multiple simultaneous clients behind the same NAT/IP, and breaks if the client's connection/port changes between calls). | design.md § Components/Modules, "Session store" bullet, line 36 vs. § Data Flow, `RequestContext.session_id`, line 81 |
| major | No error handling is specified around the log-then-respond glue itself (`build_log_record` / `log_writer.write()` / `emit_stderr_summary`) in the request lifecycle — these sit between building the response object and writing it to the socket, but outside `dispatch()`'s try/except. If the log write raises (disk full, permission error, an unserializable value reaching `json.dumps`, etc.), the exception is unhandled at exactly the point where it matters most: no HTTP response is ever sent, violating the plan's own "never crash / hang / drop a connection" invariant — on the one code path (logging) that is the entire point of the tool. Task 1 should add an explicit try/except around the log-then-respond glue (with a defined fallback, e.g. still attempt to send the HTTP response and emit a stderr line noting the log failure) as a stated acceptance criterion. | design.md § Data Flow / Interfaces, request-lifecycle pseudocode, lines ~65-68; design.md § Task Breakdown, Task 1 |
| minor | `headers: dict[str, str]` construction doesn't address that HTTP permits repeated header names; `self.headers` from `BaseHTTPRequestHandler` is a multi-value `email.message.Message`-like object, and a naive `dict(self.headers)` silently keeps only the last value for any repeated header. Worth a one-line acceptance note in Task 1 (either preserve duplicates as a list, or explicitly accept the data loss as out of scope). | design.md § Data Flow / Interfaces, `RequestContext.headers`, line 80 |
| minor | No socket/read timeout is specified for `ThreadingHTTPServer`/`BaseHTTPRequestHandler`. A client that sends `Content-Length: 1000000` and trickles bytes slowly (or never finishes) would block a handler thread indefinitely on `self.rfile.read(length)`, since nothing bounds read *time*, only body *size*. The plan's Risks section flags unbounded thread count for `0.0.0.0` deployments but doesn't address slow-read/slowloris-style hangs specifically. Worth a documented decision either way (accept the risk explicitly alongside the existing `0.0.0.0` warning, or set `self.timeout`) rather than silence. | plan.md § Risks ("ThreadingHTTPServer has no built-in connection/thread limits"); design.md (no read-timeout mention anywhere) |
| minor | Neither document specifies the exact response shape for the `405` on `GET`/`DELETE /mcp` beyond "no JSON-RPC body" — e.g. whether an `Allow` header is set, and whether the body is truly empty vs. a short plain-text message. Unlikely to block the builder but worth a one-line spec so Task 1's acceptance criteria are unambiguous. | plan.md § Approach ("Transport shape"); design.md § Task Breakdown, Task 1 |
